================================================================================
1. RESUMO EXECUTIVO
================================================================================

O Yuris é um sistema PHP 8 / MariaDB / Apache (XAMPP) rodando em
C:\xampp\htdocs\sistema_vendas.

- 133 arquivos PHP+JS+CSS (~42.500 linhas)
- 48 tabelas no banco
- 41 endpoints REST
- 15 telas
- 36 migrations sequenciadas
- Suite de testes e2e passa 12/12

Está em transição avançada para arquitetura multi-tenant:
- accounts (matriz/filial) já existem
- AccountContext + TenantGuard chamados em 39/41 endpoints
- Resource shares com granularidade (card/processo/contato/módulo)
- codigo_advogado (ADV-XXXXXX) único global

O isolamento multi-tenant funciona em 95% dos fluxos, mas tem
dependência frágil de herança via parent_id em 18 tabelas filhas
(processo_history, task_comments, etc) que NÃO têm account_id direto —
só não vazam porque o backend sempre chama TenantGuard antes.
Qualquer endpoint novo que esqueça o guard = vazamento garantido.

O sistema tem 5 vulnerabilidades CRÍTICAS que precisam ser corrigidas
ANTES de qualquer evolução para SaaS público — sendo a mais grave
users.senha_texto armazenando senhas em texto plano
(8 de 9 usuários afetados — violação LGPD/GDPR direta).

Para Painel Master e billing, o esqueleto está parcial:
- accounts.plano (string) existe
- accounts.status (enum) existe
- account_audit_log (tabela) existe

Mas FALTAM:
- plans
- subscriptions
- invoices
- feature_flags
- usage_limits
- super_admins
- E gravíssimo: accounts.status NÃO é verificado no login
  (conta suspended ainda entra normalmente)

Escala atual: 2 accounts, 9 users, 1.353 mensagens WhatsApp, 63 processos.

15. RISCOS PARA O FUTURO PAINEL MASTER
================================================================================

Painel Master = um usuário "deus" que vê TODOS os tenants.

O QUE PODE DAR ERRADO SE CRIAR AGORA:
-------------------------------------

1. Não há role super_admin separado — adicionar tipo "super_admin"
   em users.role mistura com tenant roles

2. AccountContext::fromSession() sempre puxa um account_id —
   super_admin não pertence a 1 conta. Refatorar pra
   accountId=NULL + flag separada

3. Modelos chamam Processo::find sem $accountIds — super_admin precisa
   de método separado (findGlobally) ou bypass explícito

4. Sem audit trail centralizado de ações cross-tenant —
   account_audit_log é por conta, não tem visão global

5. getAccessibleAccountIds() retorna [meu account + filiais + shares]
   — super_admin precisa retornar TODOS os accounts ativos.
   Bypass não está modelado.

6. Modais auto-open por ?open=ID — super_admin pode quebrar isolamento
   se navegar com URL antiga

7. Login não diferencia tipo de conta — UI única, super_admin entraria
   no dashboard normal


ORDEM SEGURA PRA PAINEL MASTER:
-------------------------------

1. Resolver críticos C1–C5 primeiro
2. Criar tabela super_admins (separada de users) ou flag
   users.is_super_admin TINYINT
3. Refatorar AccountContext:
   - isSuperAdmin() retorna bool
   - getAccessibleAccountIds() retorna 'ALL' quando super admin
     (e os modelos interpretam)
4. Modelos com método separado findById($id, $accountIds = null)
   onde null só é aceito se isSuperAdmin()
5. Sidebar / menu mostra "Painel Master" só pra super admins
6. Roteamento separado /master/* com middleware exclusivo

   App\Helpers\ApiResponse::ok($data), ::fail($msg, $code),
   ::unauthorized(). Hoje 9 cópias do function ok().

4. REPOSITORY PATTERN PARCIAL
   Processo::find() aceitando $accountIds é um repository light.
   Tornar OBRIGATÓRIO em todos os models críticos.

5. MIDDLEWARE ANTES DE CADA API
   Função requireAuth(), requireRole($r), requireTenant().
   Hoje cada endpoint repete AccountContext::fromSession() +
   isOwnerOrAdmin().

6. MIGRATION FRAMEWORK
   Algo como Phinx ou um runner próprio que registra qual migration
   já rodou (tabela migrations). Hoje é manual.

7. TESTS
   Só há scripts/test_multitenancy_e2e.php (12 cenários).
   Adicionar testes unitários por Model (PHPUnit ou Pest).

   pra produção, agregação dos <style> inline em :root global.

9. .ENV + DOTENV
   Biblioteca vlucas/phpdotenv ou parser simples.
   Senhas, gateway keys, cron tokens fora do código.

10. LOGGING ESTRUTURADO

22. CONCLUSÃO
================================================================================

NÃO RECOMENDO SEGUIR DIRETO PRO PAINEL MASTER.

O sistema tem bases sólidas e o trabalho recente em multi-tenancy é de
boa qualidade — mas existem 5 vulnerabilidades críticas que tornam um
lançamento SaaS público IRRESPONSÁVEL sem correção:

1. Senhas em texto plano (LGPD)
2. Log de debug expondo credenciais
3. Webhook sem autenticação
4. Credenciais hardcoded
5. Status de conta não verificado


CAMINHO RECOMENDADO:
--------------------
- 1–2 semanas de hardening (Fases 0 + 1 + 2)
- 2–3 semanas para preparar base SaaS (Fase 3)
- Aí sim Painel Master + Planos


PRA CONTINUAR EVOLUINDO O CÓDIGO SEM QUEBRAR NADA
(sem fazer SaaS público ainda), é possível seguir adicionando features
incrementalmente DESDE QUE:

- Toda nova tabela tenha account_id NOT NULL desde o primeiro dia
- Todo novo endpoint use AccountContext::fromSession() +
  TenantGuard::assertXAcessivel
- Não exponha mais nada pra public que não passe pelo middleware atual
- Não armazene senha em texto plano


JANELA PERFEITA AGORA:
----------------------
Sistema usado por 2 accounts + 9 usuários atualmente — escala muito
pequena. Janela perfeita pra fazer a refatoração estrutural agora
(Fases 0–3) antes que a base cresça e migração fique mais cara.
